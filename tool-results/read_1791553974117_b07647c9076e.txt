    62→1. Executive Summary
    63→
    64→This document is the second volume of the two-part reporting review of
    65→the Massapro Content Wizz platform. Where the companion audit (Reporting
    66→Capabilities Audit, October 2026) establishes what the platform can
    67→report on today, this volume documents how the reporting surfaces and
    68→their interface elements were built: the recurring architecture
    69→patterns, the state-handling conventions, the interaction models behind
    70→filtering, selection and bulk operations, and the accessibility and
    71→data-integrity details that define the product feel. Every practice
    72→described here was extracted from the shipped code and names the file
    73→that implements it, so the document serves both as an explanation and as
    74→an engineering reference.
    75→
    76→The headline finding is a two-speed adoption of the platform's own
    77→craft. The practices that make a surface feel finished, such as skeleton
    78→loading placeholders, designed empty states and toast feedback on every
    79→mutation, are implemented almost everywhere: eight of the nine surfaces
    80→render skeletons instead of zeros, eight confirm actions with toasts,
    81→and five carry purpose-written empty states with a next action built in.
    82→The practices that make a surface feel powerful, such as filters,
    83→multi-selection, bulk operations and labeled keyboard operation, are
    84→concentrated almost entirely in one workspace. The Plan Detail view is
    85→the only surface that implements all eight practice areas identified in
    86→this review.
    87→
    88→Between those two speeds sits a set of ten concrete, reusable patterns:
    89→server-side counting with client-owned view state; one fetch per surface
    90→with in-browser computation; live filter counts computed from the full
    91→dataset; a set-based selection model that survives filter changes; a
    92→contextual bulk bar with conditional inputs; optimistic state sync from
    93→bulk responses; sequential processing with live progress for
    94→rate-limited external calls; a six-slot reserved status color system
    95→shared through one exported badge component; honest timezone and
    96→media-snapshot fallback handling; and explicit ARIA labeling with
    97→keyboard operation. Each is small enough to apply in an afternoon and,
    98→together, they are the reason the Plan Detail workspace feels like the
    99→product's best-built surface.
   100→
   101→The review also records where the build departs from its own best rules:
   102→a computed counter that no view renders, a layout that silently ignores
   103→the active filter, a chart stack installed but never imported, and
   104→filter state that dies on navigation. Chapter 9 lists the five
   105→deviations with code evidence, and Chapter 10 compresses the whole
   106→review into a fourteen-rule acceptance checklist intended to be applied
   107→to every future reporting surface, starting with the analytics endpoint
   108→and first charts already recommended by the companion audit.
   109→
   110→2. Scope, Sources and Method
   111→
   112→The review covers the same nine user-facing surfaces as the companion
   113→audit: the Dashboard (Command Center), the Content Plans list, the Plan
   114→Detail workspace in both of its layouts, the Brands grid, the Brand
   115→Detail view with its tabs, the Media, Knowledge and AI Agents panels,
   116→and Settings. For each surface it examines not what is reported but how:
   117→how data is fetched and held, how the loading, empty and error
   118→conditions are rendered, how controls are built and labeled, and how the
   119→interface behaves when the user acts on it. The server-side counterparts
   120→that shape interface decisions, namely the /api/stats endpoint, the
   121→shared type constants and the Prisma data model, are included where
   122→relevant.
   123→
   124→The method is pattern extraction at code level. Each practice area was
   125→identified from a concrete implementation, then counted across all nine
   126→surfaces by direct search of the component sources, which produced the
   127→coverage figures used in Chapter 4 and Chapter 10. A pattern is
   128→documented only when its implementing file is named; nothing in this
   129→document is inferred from design intention or from behavior observed
   130→outside the code. The counts are deliberately conservative: a surface
   131→receives credit for a pattern only when the pattern is implemented in
   132→its own component source, not when it merely benefits from a shared
   133→dependency.
   134→
   135→Two boundaries apply. First, this is an engineering-practices review
   136→rather than a visual style guide: it documents interaction and state
   137→conventions, not the color palette, typography or iconography decisions
   138→that a design-system document would own. Second, it describes the build
   139→as shipped on the production deployment; where a better pattern exists
   140→in the dependency tree but is unused, as with the chart wrapper, it is
   141→recorded in Chapter 9 as a deviation rather than presented here as a
   142→practice.

   144→3. Architecture Patterns: How Report Data Reaches the Screen
   145→
   146→Reporting data reaches the screen through three planes, and the division
   147→of labor between them is the platform's first architectural best
   148→practice. The aggregate plane is the /api/stats endpoint, which executes
   149→its six counters in parallel with Promise.all, each scoped to the
   150→signed-in user, and returns them alongside the four most recent plans
   151→with their brand, generating agent and post counts. The entity plane is
   152→a set of plain REST lists: every surface fetches its full entity
   153→collection once and renders it. The lifecycle plane is the publish
   154→pipeline, which maintains status, scheduled date, published timestamp
   155→and the LinkedIn post URN on each post as it moves through the workflow.
   156→Table 1 summarizes the three planes.
   157→
   158→Table 1: The three data planes and their implementations
   159→
   160→  -----------------------------------------------------------------------
   161→  Plane        Implementation                      Consumed by
   162→  ------------ ----------------------------------- ----------------------
   163→  Aggregate    /api/stats runs six parallel        Dashboard KPI cards
   164→  counters     database counts scoped to the user, and lists
   165→               plus a recent-plans query (take 4)  
   166→               with brand, agent and post count    
   167→
   168→  Entity lists One REST fetch per surface; all     Plans, Plan Detail,
   169→               counting, filtering, selection and  Brands, Media,
   170→               layout derived in the browser from  Knowledge, Agents
   171→               the held array                      
   172→
   173→  Publish      Status transitions maintained by    Status badges,
   174→  lifecycle    the publish route and scheduler;    per-status counts,
   175→               URN and timestamps stored on the    calendar
   176→               post row                            
   177→  -----------------------------------------------------------------------
   178→
   179→The first practice is that the server counts cheaply and the client owns
   180→view state. The stats endpoint performs only the operations the database
   181→does best, namely parallel counts, and returns flat numbers; everything
   182→stateful, from the selected brand to the ticked posts and the active
   183→layout, lives in component state on the client. This keeps the API
   184→stateless and simple to reason about, and it frees the interface to
   185→rearrange, filter and recompute without asking the server again. The
   186→same discipline shows in the dashboard load, which fetches the stats and
   187→the brand list concurrently rather than sequentially.
   188→
   189→The second practice is one fetch per surface, computed in the browser.
   190→Every list surface holds its complete dataset in memory and derives
   191→everything the user sees, including filter options, per-status counts
   192→and row visibility, from that array at render time. The payoff is
   193→interaction latency: filters apply with no spinner because there is no
   194→round trip. The cost is equally real: payloads grow with the dataset, so
   195→the pattern has a shelf life, and the sorting, pagination and
   196→server-side filtering recommended in the companion audit become
   197→necessary as collections grow. The pattern is the right default until
   198→the data says otherwise, and knowing that boundary is part of the
   199→practice.
   200→
   201→The third and fourth practices concern honesty at the edges. Side
   202→effects that must happen for a report to be true are attached to the
   203→report itself: opening the Dashboard triggers the throttled scheduler
   204→sweep, capped at once per minute, so the counts it shows are never stale
   205→from posts that fell due while nobody was looking; the report doubles as
   206→the platform heartbeat. And the vocabulary of the interface is defined
   207→exactly once: the five workflow statuses and six post types are exported
   208→constants in the shared types module, and every filter option, bulk
   209→dropdown and editor select is generated from those arrays, so the
   210→interface cannot drift from the data model. One deliberate anti-pattern
   211→is on record alongside these practices: the endpoint computes a
   212→published counter, combining scheduled and published posts, that no view
   213→renders. The rule it violates is simple, namely that every computed
   214→field should either be displayed or deleted, and it opens the deviation
   215→register in Chapter 9.

   217→4. The UI State Model: Loading, Populated, Filtered, Empty, Error
   218→
   219→Every list surface in the platform is written against the same five
   220→states, and this convention more than any other defines the product
   221→feel. Loading renders skeletons that match the geometry of the content
   222→they replace, a small block where each KPI number will sit and
   223→full-height rows where list items will appear, so the page settles into
   224→place instead of flashing zeros or blocking on a spinner. Populated
   225→renders the data. Filtered renders the subset while the controls keep
   226→their labels truthful. Empty and error each have their own designed
   227→response. The value of the convention is trust: at no point does the
   228→interface show a number it does not yet know, or a blank where an
   229→explanation belongs.
   230→
   231→Empty states are differentiated by cause, which is the heart of the
   232→pattern. A surface with no data at all explains the situation and offers
   233→the next action in the same breath: the Dashboard brands panel states
   234→that no brands exist yet, says why the first one matters, and carries a
   235→Create Brand button; the Plans list renders a card that explains what a
   236→plan is and how to generate the first one. A surface with data but no
   237→matches says so in one line: the Plan Detail list shows an explicit “No
   238→posts match this filter.” message, keeping the cause, which is the
   239→active filter, distinct from the state, which is an empty result. This
   240→distinction prevents the most common empty-state failure, in which users
   241→cannot tell whether their data is missing or their filter is wrong.
   242→
   243→Errors are delivered as toasts with a destructive variant, and wherever
   244→a partial outcome is possible the copy reports the honest tally: bulk
   245→approvals summarize as approved nine of twelve, and bulk publishing
   246→distinguishes an all-live result from a partial one, with the likely
   247→cause and remedy in the description. Guards fire before errors do:
   248→attempting to generate a plan with no brands is intercepted by a
   249→guidance toast rather than an API failure. Figure 1 shows how unevenly
   250→this state craft is distributed across the platform: skeletons and
   251→toasts are near-universal at eight of nine surfaces, designed empty
   252→states reach five, and the interaction patterns of the following
   253→chapters remain confined to one or two surfaces.

   295→5. Filter and Control UX Patterns
   296→
   297→The Plan Detail workspace implements the platform's complete filter
   298→vocabulary, and its choices generalize into rules that any new reporting
   299→surface can adopt unchanged. The controlling principle is that filters
   300→must be truthful, scoped and consistent: truthful in what their labels
   301→claim, scoped to every layout that renders the same entities, and
   302→consistent in geometry and placement across the toolbar. The three
   303→subsections below extract those rules from the shipped implementation,
   304→and Table 3 collects the conventions in reviewable form.
   305→
   306→5.1 Live counts computed from the full dataset
   307→
   308→The status filter is a compact select whose options carry counts, All
   309→(30), draft (12), approved (7), and the counts are computed from the
   310→full posts array, never from the visible subset. The distinction matters
   311→more than it looks. Had the counts been derived from the filtered list,
   312→choosing a status would shrink every other option's count and could
   313→dead-end the user in a state they could neither reason about nor escape.
   314→Computing from the full array keeps each option's count stable and
   315→truthful no matter what is selected, which is what makes the control a
   316→reporting instrument rather than a view toggle. The general rule:
   317→counter labels inside a filter describe the whole dataset, not the
   318→filtered remainder.
   319→
   320→5.2 Filters bind to every layout, or announce otherwise
   321→
   322→The workspace has two layouts, list cards and a thirty-day calendar
   323→grid, and the status filter drives only the first. The calendar always
   324→draws all thirty day cells from the full dataset, so switching layouts
   325→silently discards the active filter without a warning of any kind. The
   326→best-practice form of this rule is stated positively: a filter applies
   327→to every layout that renders the same entities, and where a layout
   328→intentionally ignores it, as the calendar does to preserve its
   329→month-at-a-glance reading, the interface must say so rather than leave
   330→the mismatch to be discovered. This is the one documented violation of
   331→the platform's own filtering rules, and it stands first in the deviation
   332→register of Chapter 9.
   333→
   334→5.3 Control geometry and placement
   335→
   336→Controls follow a consistent, teachable geometry. Header-level
   337→selectors, such as the brand filter on the Plans list, sit beside the
   338→primary action in the page header at a fixed width with an explicit All
   339→option first and All as the default on every visit. Workspace-level
   340→controls, such as the status filter and the select-all checkbox, sit in
   341→a compact 32-pixel toolbar row directly above the content they filter,
   342→close enough that cause and effect are visually connected. Layout
   343→switching between list and calendar is a first-class dropdown with icon
   344→entries rather than a hidden toggle, and each control that filters list
   345→data keeps that list's empty state within the same block. Table 3
   346→summarizes the conventions.

   374→6. Selection, Bulk Operations and Feedback Loops
   375→
   376→Selection is stored as a set of stable post identifiers, and that single
   377→decision carries the whole pattern. Because membership is keyed by id
   378→rather than by position or current visibility, selections survive filter
   379→changes: an operator can filter to drafts, tick a batch, switch the
   380→filter to approved, add more posts, and apply one bulk operation to the
   381→union, a behavior the code comment documents as intentional. Select-all
   382→operates on the visible subset and is labeled accordingly as selecting
   383→all visible posts, so its promise matches its reach. The set is cleared
   384→only by an explicit Clear action or by the operation itself succeeding,
   385→never silently by a refetch.
   386→
   387→The bulk bar is contextual and conditional. It does not exist until at
   388→least one post is selected, and it then appears as a distinct panel
   389→showing the selection count, the status dropdown, and Apply and Clear
   390→buttons. Choosing the scheduled status expands three further inputs in
   391→place, a start date, a publishing time defaulting to nine in the
   392→morning, and a posts-per-day selector from one to four, so the bar grows
   393→only as the task grows. Context-conditional buttons follow the same
   394→logic elsewhere in the toolbar: the approve-all action renders only when
   395→drafts exist and the publish-approved action only when approvals do,
   396→each carrying its live count in the label.
   397→
   398→Applying a bulk operation trusts the response and updates in place. The
   399→bulk endpoint returns the updated rows and a skip count; the client
   400→merges them into local state without a refetch, so the interface
   401→responds instantly and the filter's live counts move with the change.
   402→Where an external service sets the pace, processing is sequential with
   403→live progress: publishing approved posts walks them one at a time, the
   404→button label reading publishing three of twelve as it goes, pacing
   405→requests to respect rate limits on the LinkedIn side. Partial failure is
   406→tolerated and reported rather than treated as an abort: approvals
   407→proceed item by item under an explicit keep-going policy, and the
   408→closing toast states the honest tally with the failure cause and remedy
   409→in its description.
   410→
   411→The feedback loop closes in the copy. Toasts restate computed results in
   412→plain language: the schedule confirmation repeats the start date, the
   413→per-day rate and any skipped posts, so the user can verify what was
   414→actually set without reopening anything. Copy-to-clipboard flips its
   415→confirmation state for one and a half seconds before reverting, a
   416→feedback duration sized to the smallness of the action. Long-running
   417→generation is polled every three seconds while the plan status is
   418→generating, the progress bar holds a visible four-percent floor so it
   419→never looks frozen at zero, polling stops at the first terminal status,
   420→and completion or failure is announced with a toast. The rule that
   421→covers all of these: every user action ends in a stated, checkable
   422→outcome.

   424→7. The Status Visualization System
   425→
   426→Workflow status is the platform's most information-dense field, and it
   427→is rendered through one shared system of reserved hue slots. Six
   428→statuses own six colors: draft zinc, approved emerald, scheduled sky,
   429→published purple, failed red, and publishing amber, with amber
   430→deliberately reserved for the transient in-flight state, so that an
   431→amber card always means something is happening to that post right now.
   432→The color rides a four-pixel left border on each post card, which lets a
   433→plan read as an informal heatmap of workflow state when scanned
   434→vertically. Table 4 records the slots and their semantics.
   435→
   436→Table 4: The six reserved status slots and their semantics
   437→
   438→  ------------------------------------------------------------------------
   439→  Status         Color slot        Semantics
   440→  -------------- ----------------- ---------------------------------------
   441→  DRAFT          Zinc              Generated content awaiting review
   442→
   443→  APPROVED       Emerald           Cleared for publishing
   444→
   445→  SCHEDULED      Sky               Holding a future publish time
   446→
   447→  PUBLISHING     Amber (transient) Publish call in flight; guarded against
   448→                                   re-entry
   449→
   450→  PUBLISHED      Purple            Live on LinkedIn, with URN and
   451→                                   timestamp stored
   452→
   453→  FAILED         Red               Terminal failure with the cause stored
   454→                                   on the record
   455→  ------------------------------------------------------------------------
   456→
   457→Color is never the only channel. Every card also carries a lowercase
   458→text badge of its status, so the state survives color-blind reading,
   459→printing and screenshots. The badge component itself is shared: the plan
   460→status badge is defined once in the Dashboard component and imported by
   461→both the Plans list and the Plan Detail workspace, which is why a
   462→generating plan shows the same spinner-plus-progress chip, reading
   463→twelve of thirty, everywhere it appears. The rule is one status, one
   464→badge, one definition: surfaces consume the component, they do not
   465→restyle the concept.
   466→
   467→The same single-source discipline covers post types, rendered through a
   468→lookup record that maps each of the six types to an icon with a safe
   469→text fallback for anything unknown, and it extends to action
   470→affordances: the one-click publish action wears LinkedIn's own brand
   471→blue rather than the application purple, reserving the platform color
   472→for platform-state actions and the network color for the network
   473→boundary. Empty calendar days complete the system as deliberately
   474→designed absences, drawn as dashed, non-interactive placeholders that
   475→carry no button role and no tab stop, so keyboard users skip them
   476→entirely.

   478→8. Accessibility, Responsiveness and Data Integrity
   479→
   480→8.1 ARIA labels and keyboard operation
   481→
   482→The Plan Detail workspace is the platform's accessibility reference
   483→implementation. Every control that would otherwise be unnamed carries an
   484→ARIA label: the bulk status select, the schedule date, time and
   485→posts-per-day inputs, and every row checkbox, which is labeled with the
   486→post's own hook or day number rather than a generic select. Cards and
   487→calendar cells that behave as buttons declare the button role, take a
   488→tab stop, and bind both Enter and Space in addition to click, while
   489→checkbox clicks are stopped from propagating so that ticking a row does
   490→not open it. No other surface currently matches this standard, which is
   491→precisely why it is documented here as the pattern to copy rather than
   492→an exception to forgive.
   493→
   494→8.2 Responsive behavior
   495→
   496→Layouts compress by reordering rather than by hiding features. The KPI
   497→row steps from six columns on desktop to three on tablets and two on
   498→phones, keeping every card reachable without horizontal scroll. The post
   499→editor's two-column grid collapses to a single column on medium screens
   500→with the media panel moving below the copy; per-post scheduled datetimes
   501→hide on small screens where they would crowd the row, while the same
   502→information stays available inside the editor dialog. Header toolbars
   503→stack vertically on mobile before they would wrap awkwardly. The rule:
   504→the small-screen arrangement is designed, not an overflow.
   505→
   506→8.3 Timezones, snapshots and save-order integrity
   507→
   508→Three quiet correctness patterns protect the data behind the interface.
   509→Scheduling inputs use the browser's datetime-local value built in the
   510→user's local timezone by an explicit conversion helper: the server
   511→stores ISO instants, the interface renders local wall-clock time, and
   512→the two never blur. Media attachment follows a documented fallback
   513→chain, from the freshly generated in-memory preview, to the attachment's
   514→file URL, to the inline data snapshot stored on the post itself, so
   515→images survive serverless instance recycling, and legacy posts carrying
   516→only an asset reference still show an honest attached state instead of a
   517→broken image. And the publish action saves the editor's current form
   518→before it publishes, which guarantees that the post that goes live is
   519→the post the user was just looking at.

   576→10. The Best-Practices Checklist and Conclusions

   579→new reporting surface, including the analytics endpoint and first charts
   580→recommended by the companion audit, is done when every line can be
   581→answered yes at code review. Each rule names where it is checked so the
   582→list can be applied without this document in hand.

   631→
   632→The conclusion of the review is that the discipline which makes the Plan
   633→Detail workspace the platform's best reporting surface, honest counts, a
   634→selection model that cooperates with filtering, reserved status
   635→semantics, named controls and stated outcomes, is not expensive, and six
   636→of its fourteen rules are already platform-wide. The gaps are coverage
   637→and consistency rather than invention: every pattern in this document
   638→exists, works and is named in the shipped code. Building the next
   639→reporting features under the same rules, with the checklist as the merge
   640→gate, turns each new surface into an increment of one product rather
   641→than a fresh set of decisions.
   642→
   643→The recommended first application of this document is the
   644→highest-priority work package from the companion audit: the analytics
   645→endpoint and the first two dashboard charts. That package should land
   646→with the same state craft the rest of the platform already enjoys,
   647→skeletons on load, a designed empty state before the first data arrives,
   648→and toasts that restate what was computed, because the first chart a
   649→stakeholder sees will set their expectation of every chart that follows.
